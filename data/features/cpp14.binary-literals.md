## 解决什么问题

处理协议、编码和寄存器时，代码里到处是位掩码。用十六进制写 `0xF0` 需要先在脑子里展开成 `11110000`，再核对哪些位被置上；用 `1u << 4 | 1u << 5 | 1u << 6 | 1u << 7` 又啰嗦且容易漏掉一位。两种写法都把“位的布局”藏在计算后面，评审时很难一眼看出它对应规范里的 `11110xxx` 还是 `1110xxxx`。

C++14 的二进制字面量（N3472）直接允许 `0b` 前缀加 0/1 序列。它只是一个字面量写法：编译期换算成整数值，运行时没有额外开销，类型规则与十进制、十六进制字面量完全一致。对于 UTF-8 前导字节、Base64 分组标志、硬件寄存器位段这类“每一位都有含义”的数据，二进制写法让代码本身成为位图。

## 基础用法

二进制字面量可以出现在任何整数常量允许的位置，也可以与按位运算直接组合。

<!-- compile -->

```cpp
#include <cstdint>
#include <iostream>

int main() {
  const std::uint8_t value = 0b10101010;
  const std::uint8_t high = value & 0b11110000;
  std::cout << static_cast<int>(high) << '\n';
}
```

`value & 0b11110000` 保留高四位，结果是 `0b10100000`，即 160。完整示例见 [`examples/cpp14/binary_literals.cpp`](../../examples/cpp14/binary_literals.cpp)，五个场景的输出为：

```text
[1] flags = 10
[2] mask = 240
[3] low nibble = 6
[4] utf8 tail = 0x80
[5] leading bits = two
```

场景 1 用 `0b00001010` 表示一组开关，最低位和高三位为假、中间位为真，十进制结果是 10。场景 2 的 `0b11110000` 是常见的高四位掩码。场景 3 用 `byte & 0b00001111` 取低半字节，`0b10110110` 的低四位是 `0110`，所以输出 6。场景 4 把 UTF-8 续字节固定前缀 `10xxxxxx` 中的标志位写成 `0b10000000`，十六进制输出为 0x80。场景 5 对高位右移后交给 `switch`，`case 0b10` 直接表达“最高两位为 10”的条件，可读性来自字面量而不是注释。

## 进阶用法

**字面量的类型规则与其他整数字面量相同。** 一个没有后缀的 `0b11111111` 类型是 `int`（能容纳 255），不是 `uint8_t`；需要无符号或更宽类型时加 `u`、`l`、`ull` 等后缀，或显式转换。字面量的前导零只影响视觉对齐，不改变数值或宽度。

**与数字分隔符组合。** C++14 同时加入单引号数字分隔符（N3781），`0b1101'0011'1010'0101` 可以按半字节或寄存器字段分组。分隔符只提高可读性，解析时被忽略。

**用特性宏做条件编译。** 库需要兼容 C++11 或更早的编译器时，检查 `__cpp_binary_literals`（值为 `201304L`）；宏不存在时退回十六进制写法。老版本 GCC 把 `0b` 当作 GNU 扩展接受，但在 `-pedantic` 下仍会报警，不能把“能编译”当成标准支持。

**用 `switch` 匹配位段。** 先移位或掩码，再用二进制字面量写 `case`，能让分支条件与协议字段定义逐位对应。对于状态机或编码分类，这比十六进制常量更容易核对。

**与 `std::byte` 配合要显式转换。** `std::byte` 是枚举类，不能直接从整数隐式构造；需要写成 `static_cast<std::byte>(0b10101010)`。这时二进制字面量仍然负责表达位图，类型安全由 `std::byte` 负责。

## 陷阱与边界

- **C++11 及更早不合法。** 标准模式下 `0b` 不是 C++11 词法的一部分；旧 GCC 接受它只是 GNU 扩展，开启 `-pedantic` 会报警。GCC 4.9、Clang 2.9、MSVC 19.0 起提供标准支持。
- **字面量不携带宽度。** `0b0000000011111111` 仍是 `int`，前导零不会让它变成 `uint16_t`。需要固定宽度时用 `<cstdint>` 类型和显式转换。
- **二进制与八进制容易混淆。** `0b` 前缀是二进制，单个前导 `0` 是八进制；`010` 等于 8，`0b010` 等于 2。
- **没有负的二进制字面量。** 负号是作用于字面量的一元运算符，`-0b101` 合法但类型规则要先确定字面量本身的类型。
- **`~` 作用于窄类型会先整型提升。** `~std::uint8_t{0b00001111}` 的结果是 `int` 的按位取反，不是 8 位的 `11110000`；需要时先转换再掩码。
- **不要用它写超长随机常量。** 只有位段有语义时二进制才有优势；普通数值常量用十进制更短，长二进制串可以用数字分隔符分组但仍难读。
- **工具链下限。** GCC 4.9（4.3 起仅为 GNU 扩展）、Clang 2.9、MSVC 19.0 起在 C++14 模式下支持；更早工具链需要十六进制或移位写法。

## 横向对比

| 写法                | 位布局可读性 | 编译期取值 | 运行时开销 | 主要限制                           |
| ------------------- | ------------ | ---------- | ---------- | ---------------------------------- |
| 二进制字面量        | 高           | 是         | 零         | 仅 C++14 起，长常量仍占篇幅        |
| 十六进制字面量      | 中           | 是         | 零         | 需要在大脑中展开位段               |
| 移位与按位或表达式  | 中           | 是         | 零         | 冗长，漏写一位不会报错             |
| 八进制字面量        | 低           | 是         | 零         | 与现代位布局习惯不一致             |
| 运行时字符串解析    | 取决于实现   | 否         | 解析开销   | 引入错误处理，常量无法参与模板参数 |
| 二进制 + 数字分隔符 | 高           | 是         | 零         | 仍需 C++14，只改善分组不改变长度   |

二进制字面量最适合“每一位都有协议含义”的常量。普通数值、地址和长度仍用十进制，密集位段用十六进制或二进制加分隔符；判断标准是读者能否不借助注释还原位图。
